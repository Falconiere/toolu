# Native release runbook

`release-please.yml` owns version bumps and tags. Its Release PR updates the root package, the npm wrapper package, Cargo workspace and lockfile, and every plugin manifest. Merging it creates a draft GitHub Release and the tag in one run, which calls `release-native.yml` and, after it succeeds, `npm-publish.yml`. `@toolu/plugins` publishes a deprecation notice with no binaries, and a stable publish then marks every version deprecated. A native failure therefore leaves npm unpublished. The native release never waits for npm, because npm makes a version visible minutes after accepting a publish with no published bound (8.1.1 took 8 minutes 11 seconds, and the old npm-first chain left that release a draft with no binaries). `npm-publish.yml` ends its publish job when npm accepts the upload; its `verify` job, which nothing waits for, polls the registry's uncached per-version document for up to 30 minutes. The release is never public before native finalization.

## Native assets

The native build matrix runs on `macos-14` (Darwin arm64), `macos-15-intel` (Darwin amd64), `ubuntu-24.04` (Linux amd64 musl), and `ubuntu-24.04-arm` (Linux arm64 musl). Every build uses the pinned toolchain and `cargo build --release --locked --bin toolu`. Each `toolu-<os>-<arch>.tar.gz` has two root members: executable `toolu` and `LICENSE`. The release also carries `SHA256SUMS`, its minisign signature `SHA256SUMS.minisig`, `toolu.spdx.json`, `install.sh` from the tagged commit, and GitHub build provenance attestations for the four archives. `get.toolu.sh/pkg/toolu/install` redirects to `https://github.com/Falconiere/toolu/releases/latest/download/install.sh`, so the one-liner always runs the installer of the latest stable release, which trusts the key that signed it. `check-workflows` fails if `release-native.yml` stops packaging or uploading it. That asset is the trust root of the one-liner, and nothing signs it: anyone who can write releases in this repository can replace it with `--clobber`, and the next one-liner run executes it. The old commit pin needed a second change, in `CodaSignal/toolu.sh`; the redirect does not. A stable release published from an older draft keeps `--latest=false`, so it cannot move Latest, or the served installer, backwards. The package job signs `SHA256SUMS` with the `TOOLU_MINISIGN_SECRET_KEY` secret, using the minisign 0.11 archive `install.sh` pins, and verifies the signature against the public key `install.sh` embeds; a missing secret fails the job before anything is uploaded. The trusted comment is `toolu <tag>`, and `install.sh` requires it, so an older release's signed files are refused under a newer tag. The secret holds the whole secret-key file of a key made with `minisign -G -W` (no password: CI has no terminal to type one). Rotating the key means a new `TOOLU_PUBLIC_KEY` in `install.sh` and a release signed with the new key, which also carries that `install.sh`. A pinned commit cannot be edited, so an `install.sh` fetched from an old commit keeps trusting the old key: if that key leaks, also delete the `SHA256SUMS.minisig` of every release it signed, re-sign those releases with the new key, upload the new `install.sh` to the latest release with `gh release upload <latest tag> install.sh --clobber` (or cut a release signed with the new key), and announce the rotation. `get.toolu.sh` serves the latest release's `install.sh`, so until that asset changes the one-liner keeps trusting only the leaked key and refuses the re-signed release. The installer and Homebrew formula (#457) consume this layout.

The upload job downloads the draft Release's assets back and byte-compares them with the packaged artifact. The reusable finalizer then smoke-tests that same artifact, because a draft is visible only to a write token and no token reaches the jobs that run the built binary. It checks the checksum and layout, runs `toolu --version` against the tag, verifies the Darwin code signature, and runs each static Linux binary in Alpine and Debian. Only after all four legs pass does the workflow publish the draft. A tag containing `-` becomes a prerelease, so GitHub's stable `latest` stays on the previous release; npm uses its `next` dist-tag instead of moving `latest`. After the native release succeeds, release-please calls `release-homebrew.yml`, which regenerates `Formula/toolu.rb` with `cargo xtask homebrew-formula <tag> SHA256SUMS` and pushes it to `Falconiere/homebrew-tap` with a token minted from `HOMEBREW_APP_ID` and `HOMEBREW_APP_PRIVATE_KEY`, scoped to the tap. It first verifies `SHA256SUMS.minisig` for the tag, as the installer does. A manual dispatch with a `tag` input updates the tap for a release that a manual `release-native.yml` run published. Its job is skipped for a tag that contains `-`, so a prerelease leaves the tap unchanged.

## Dry run

Dispatch `release-native.yml` with `publish=false` and an existing test tag of the form `vX.Y.Z-test` or `vX.Y.Z-test.1`, where `X.Y.Z` equals the workspace version at that tag. The dispatch builds the four binaries, packages them, and runs the same finalizer against the workflow artifact. It does not upload assets or publish a Release. The test tag must point to a commit with this workflow and its source; creating tags is separate from this worker's issue authorization.

## Failure and recovery

The repository variable `TOOLU_RELEASE_DISABLED=true` stops the automatic release-please job. If the native build, upload, or finalizer fails, the GitHub Release remains a draft and cannot replace stable `latest`. Inspect the failed job. For a transient runner or upload failure, dispatch `release-native.yml` with the same exact release tag and `publish=true`; it requires the existing draft, replaces its named assets, verifies them, then publishes. That run does not publish npm, so then dispatch `npm-publish.yml` with the same tag. If source code or dependency repair is needed, do not move the release tag: keep the draft and cut a later release through a new Release PR. npm publishes only after the native release, so a native failure never leaves an npm version behind. If the npm `publish` or `verify` job is red, the native release is unaffected: dispatch `npm-publish.yml` with the same tag. It skips a version already on the registry, deprecates every version when the tag is stable, and verifies again. The weekly advisory audit checks `Cargo.lock` at the latest stable tag.

## Manual deploy

While GitHub Actions is unavailable, a maintainer can cut the same signed release from a Mac by typing the Claude Code skill `/deploy --env prod --tag <tag> --change-log "<notes>"` (`.claude/skills/deploy/SKILL.md`). The skill sets `disable-model-invocation`, so only a user can start it. An agent then follows its eleven steps: inputs, preflight, gate, Darwin builds, Linux builds, package and sign, smoke test, publish, tap and release PR, install check, and report. It stops at the first failed check, and nothing is public before the publish step. It cuts production releases only: `prod` is the one accepted environment, and there is no dev or rc channel.

The skill never bumps versions. release-please's PR must already be merged, and `HEAD` must equal `origin/main`. With CI off, run `npx release-please release-pr` locally to open that PR, then merge it with admin rights. The tag must equal `v<workspace version>`. The skill publishes a stable release, updates `Falconiere/homebrew-tap`, and relabels the merged release PR from `autorelease: pending` to `autorelease: tagged`, so release-please does not try to release the version again once CI returns. `--change-log` becomes the release notes.

Preconditions are minisign, zig, `cargo-zigbuild`, the Infisical CLI, Docker, Rosetta, and the Rust targets `x86_64-apple-darwin`, `aarch64-unknown-linux-musl` and `x86_64-unknown-linux-musl`. rustup's `cargo` must come before Homebrew's on `PATH`. Darwin binaries build with `cargo build`, and Linux musl binaries with `cargo zigbuild`, both on the host. Docker runs the gate container and the Alpine and Debian smoke tests, with each input fed through stdin rather than a `/Volumes` bind. The skill signs `SHA256SUMS` with `TOOLU_MINISIGN_SECRET_KEY` from Infisical (project `toolu`, env `prod`), streaming it straight into `minisign`, and verifies the result against `install.sh`'s key. A manual release carries no SBOM and no build provenance attestation, and it does not publish npm.

The gate cannot be waived. `cargo xtask deploy-gate` repeats the CI `verify` job: the release-helper unittests and the full `cargo xtask gate`. It runs on a `git bundle` of a clean `HEAD`, taken before the image build, as uid 501 in `/src` building with every CPU of the Docker VM but testing with CI's 4 nextest threads (on Colima, the `toolu-gate` profile has 8 CPUs; see below), inside the `toolu-deploy-gate:<channel>` image it just built, addressed by image ID, built from `rust:<channel>-trixie` with `release-native.yml`'s tool pins plus `npx`, `jq` and `gh` (which the tests run, as on GitHub's runner image), so a Homebrew `toolu` or a `/Volumes` target directory on the host cannot break it. The first run builds the image, which takes a long time and needs several GB of free Docker disk. A full disk stops the release. With Colima, give the gate its own profile so it does not starve or restart the shared one: `colima start toolu-gate --cpu 8 --memory 8 --disk 60`, then `docker context use colima` (the start switches the global context), and run the gate with `DOCKER_CONTEXT=colima-toolu-gate`. A pass writes `target/deploy/gate.json` with the gated commit. Named volumes (`toolu-deploy-gate-target`, `-registry`, `-git`) keep cargo's target directory and download caches between runs, so reruns skip most of the build while the checkout stays fresh. As with CI's rust-cache, only dependency builds are reused: each run takes a lock on the target volume and first cleans the workspace's own artifacts; `docker volume rm` them to start cold. The run holds the container's stdin open until the container exits, and the container stops its gate when stdin closes, so killing `deploy-gate`, even with `SIGKILL`, leaves no container behind. The skill's frontmatter declares a `PreToolUse` hook on Bash and the file tools that stays registered for the rest of the session. It runs the guard on every call: `deploy-gate` first snapshots its own binary to `.claude/tmp/deploy-guard`, and the hook runs that binary directly, so neither a later checkout nor a broken build can lock the session out. Before the snapshot exists, the hook runs `cargo xtask deploy-guard`. The guard blocks a tag push, a `gh release` write, a push from another repository (`-C`, `cd`, `env -C`, `--git-dir`, `GIT_DIR`, or a `cwd` left in the tap by an earlier call), a push whose refspec or remote config can send tags, and the `autorelease` relabel unless that receipt names the current clean `HEAD` and `HEAD` equals `origin/main`. It also checks that a pushed tag, or a `gh release --target`, points at `HEAD`, and treats a git alias that pushes as a push. It always blocks a write to the receipt or the snapshot (from the shell parser's write targets and `ln`, case-folded with `..` resolved, so reading the receipt is fine) and a tag on a commit other than `HEAD`. `onFailure: block` also blocks when the guard fails to build or times out. The guard reads command text through toolu's shell parser, so `gh api` writes and forms it does not recognize are not gated, and it gates only agent tool calls in Claude Code, not a terminal. If a step fails after the tag push, the release stays a draft. The skill reports `gh release delete <tag> --cleanup-tag --yes` and `git tag -d <tag>` and runs them only on request. When `HEAD` has moved, the guard blocks `gh release delete` too, and the user runs it with the `!` prefix.
